Vela validation

Routine checks (run from the repository root):
  swift build -c debug
  swift test
  node --test Tests/WebClient/*.test.cjs
  python3 scripts/check-localization.py
  python3 scripts/check-companion.py
  python3 -m unittest discover -s Tests/Release -p 'test_*.py'
  .build/debug/Vela --check-settings-controls
  .build/debug/Vela --watch-policy-test
  .build/debug/Vela --self-test

Settings visual review (private preferences and remote files; no power assertions,
hotkey registration, remote listener, or real login-item changes):
  .build/debug/Vela --settings-review --settings-appearance light -velaLanguage en
  .build/debug/Vela --settings-review --settings-appearance dark -velaLanguage zh-Hans
  .build/debug/Vela --settings-review --settings-appearance contrast-dark --settings-opaque
Use --settings-page general|keepAwake|agent|appearance|remote to select a page.
Language changes in this review window are process-only. Close the review window
before launching another review. Check all five pages at minimum window size,
native slider keyboard access, navigation history, and both languages. There is
no settings search field. Chinese navigation titles each contain two characters.

The native self-test briefly creates real IOKit power assertions and test windows,
then releases them. It uses isolated preferences, remote settings, and login-item
fakes. Live Metal drawable checks need a visible desktop; an obscured window makes
those checks INCONCLUSIVE. These tests do not prove real unattended lock behavior.
The native language switching check restores the original language selection.
The focused --check-settings-controls command verifies native compact switches,
hover scrollbar rendering, and stable scrolling with a hidden window. It creates
no hotkeys, power assertions, or remote services and can run alongside Vela.
Run the full --self-test in an isolated desktop session to avoid conflicts with
another running Vela instance's hotkeys and real pointer/focus state.

Browser fixtures (no real desktop capture, display changes, or input injection):
  python3 Tests/WebClient/mock-server.py --port 8769
Open http://127.0.0.1:8769 in a fresh browser context. Load these scripts and call:
  /language-tests.js -> await runLocalizationChecks()
  /session-tests.js  -> await runPrivateSessionChecks()
  /touch-tests.js    -> await runTouchChecks()
  /codec-tests.js    -> await runCodecFallbackChecks()
  /zoom-tests.js     -> await runZoomChecks()
  /virtual-tests.js  -> await runVirtualPresetChecks()
  /layout-tests.js   -> await runResponsiveLayoutChecks()
Run language checks first, on a fresh page. Also check a narrow/mobile viewport.
Run layout checks at 320, 360, 390, 430, 768, 800, 844, 1024, 1100, 1101, 1280,
and 1440 CSS pixels, including a short landscape viewport. These check both
languages, toolbar label bounds and reachability, status/metrics separation,
all panels, keyboard screen space, collapse/expand, and session continuity.
Virtual preset checks use mocked display responses to verify all 18 presets with
and without HiDPI, localized option groups, logical-size summaries, request
dimensions, custom-size rejection, and session continuity. They create no real
displays. Swift and Node tests cover portrait/landscape HiDPI boundary validation.
Language switching must retain connections and input values, and default to English
without an existing selection. Native/web translation catalogs must remain identical.
Codec checks inject a verified HEVC receiver with stalled decoding, then require
an authenticated H.264 replacement with restored input and no reconnect loop.

Bundle validation:
  zsh -n scripts/build-app.sh scripts/package-ci.sh scripts/create-dmg.sh
  VELA_VERSION=1.2.3 VELA_BUILD_NUMBER=1 ./scripts/package-ci.sh
The CI packaging command without signing secrets creates unsigned testing DMG and ZIP files
under .build/ci-release and does not replace dist or the installed app. Check both
bundle versions, the embedded controller, and SHA256SUMS. The release tests assert
tag-only triggers, manual tag requirements, tag/checkout matching, safe metadata,
and failure for partial signing configuration. A cloud run requires an existing
version tag; do not create a production tag solely to test the workflow.
The disk-image test builds a tiny fixture image, mounts it read-only without
opening Finder, verifies the app/controller bytes and Applications link, then
detaches it. For a real bundle, also verify codesign after mounting the DMG.
  ./scripts/build-app.sh release Vela
  codesign --verify --deep --strict dist/Vela.app
  plutil -lint dist/Vela.app/Contents/Info.plist
  ./scripts/build-app.sh release Vela --offline-check

Packaging must include Vela_Vela.bundle, Vela_RemoteServer.bundle, and
Vela_VelaLocalization.bundle, plus the controller and both languages of localized
InfoPlist.strings. The controller also needs its localization resource bundle.

Intrusive live tests are not routine validation:
- scripts/verify-lid-live.sh changes real pmset state and requests administrator
  approval. Preserve the initial setting and verify watchdog recovery afterward.
- --physical-blackout-probe changes real physical/virtual displays. Its recovery
  watchdog must be ready before disabling physical displays.
- --remote-session-probe / --remote-web-probe may require real capture/input access.
  Historical detach/lock-first prototypes can switch sessions and require local login.
- --remote-display-watchdog is an internal temporary recovery process, not a normal
  user command.
Only run these when the requested task includes the corresponding real-device test.

Desktop streaming quality (synthetic, no desktop capture or input injection):
  swift test --filter RemoteStreamQualityTests
  swift test --filter DesktopStreamMetricsTests
  swift test --filter RemoteServerTests.testWebRTC4KVideoAndControlOverRealPeerConnection
  node --test Tests/WebClient/lossless.test.cjs
These cover pressure/recovery hysteresis, viewport budgets, bounded refinement,
interval/reset statistics, native and browser stale-tile rejection, HEVC hardware
probe gating, and actual H.264 SEI identity through encrypted 4K RTP transport.
The optional browser harness is skipped during routine swift test. To exercise
real browser decoding and synchronized PNG composition, run in two terminals:
  VELA_SYNTHETIC_BROWSER_PORT=18873 VELA_SYNTHETIC_BROWSER_INFO=/tmp/vela-synthetic-browser-info.json swift test --filter DesktopBrowserTransportTests
After the info file appears, within 50 seconds run:
  python3 Tests/WebClient/synthetic-stream-server.py --info /tmp/vela-synthetic-browser-info.json --port 18773
Open http://127.0.0.1:18773 in a browser. Inspect window.result: complete must be
true and frames, markers, and draws must be positive. The proxy trusts only the
fixture's generated public certificate and binds only to loopback. Both ends use
synthetic pixels; no real credentials, capture permission, or input are involved.
Stop the Python fixture after the test. These are correctness smoke tests, not a
measurement of screen-to-screen latency, real-network recovery, or battery cost.

Streaming implementation and acceptance limitations are recorded in
Design/vela-stream-quality-2026-11-03.md. Live ScreenCaptureKit hot updates, native
window compositing, shaped-network performance and long sessions need separate
real-device acceptance. HEVC hardware support alone is insufficient: the pinned
WebRTC transport uses Vela's hardware H.265 adapters after a verified 4K adapter round trip; unsupported peers retain H.264.

Hardware HEVC transport and fallback (synthetic pixels, no TCC or desktop changes):
  swift test --filter DesktopHEVCTransportTests
This verifies actual encrypted 4K H.265 encode/decode implementations, image
contrast after live resizing, control delivery, negotiated level limits, malformed
NAL rejection, and actual H.264 reception for unsupported peers or failed HEVC
encoder initialization. Hardware-specific cases skip only if hardware is absent.

For real-browser 4K HEVC, use the optional browser harness above with:
  VELA_SYNTHETIC_BROWSER_HEVC=1 VELA_SYNTHETIC_BROWSER_PORT=18873 VELA_SYNTHETIC_BROWSER_INFO=/tmp/vela-hevc-browser-info.json swift test --filter DesktopBrowserTransportTests
  python3 Tests/WebClient/synthetic-stream-server.py --info /tmp/vela-hevc-browser-info.json --port 18773
Within the fixture's 50-second window open http://127.0.0.1:18773. window.result
must show complete=true, codec=video/H265, width=3840, height=2160, frames>0 and
hardwareCapability=true. runtimeHardwareReported may be null because browsers
can omit runtime hardware-decoder statistics; it must not be false. The native
adapter always requires hardware acceleration. HEVC-specific evidence is in
Design/vela-hevc-end-to-end-2026-11-04.md; the November 3 record is historical.

Remote detail zoom (no desktop capture or system input injection):
  swift build -c debug
  .build/debug/VelaConnect --viewport-test
The viewport test uses a hidden native window and generated events delivered only
to the test view. It checks Retina pixel mapping, 400% display sizing, bounded
Metal drawable resolution, native clip-view panning, input coordinates after
panning, ordinary scroll forwarding, view-only input blocking, and return to fit.
It starts no remote host, posts no system events, and does not verify live video
presentation. Run /zoom-tests.js on the browser fixture after language checks at
desktop and narrow/mobile sizes. It also checks source-quality feedback, touch
inspection with remote input paused, authentication continuity, and localization.
Current acceptance is in Design/vela-remote-zoom-2026-11-04.md.
